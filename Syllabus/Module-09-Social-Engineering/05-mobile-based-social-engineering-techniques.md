# 05 — Mobile-Based Social Engineering Techniques

> Exam objective: *Explain various mobile-based social engineering techniques*

Mobile-based SE relies on smartphones — their app ecosystems, SMS channel, and camera/QR-scanning
capability — as the delivery mechanism. Because mobile users tend to trust app-store curation and
rarely inspect a URL as carefully as they might on a desktop, this category is a growing share of
real-world SE incidents.

---

## 5.1 Publishing Malicious Apps

```
Attacker creates malicious app  →  Publishes on app store using a popular-sounding
(e.g., an appealing "gaming        name and attractive feature list
app")
        │
        ▼
User discovers it, believes it's genuine, downloads and installs it
        │
        ▼
App infects the device with malware → exfiltrates credentials, contacts,
and other data to the attacker
```

The attacker creates an application with attractive features and a name/icon deliberately similar
to a popular app, then submits it to major app stores. Unsuspecting users download it believing
it to be legitimate; once installed, it quietly harvests credentials and personal data.

## 5.2 Repackaging Legitimate Apps

A more insidious variant that piggybacks on **real** developer work:

```
1. Legitimate developer builds a real app and uploads it to the official app store
2. Malicious developer downloads that legitimate app
3. Malicious developer decompiles it, injects malware, and repackages it
4. The trojanized copy is uploaded to a third-party/unofficial app store
5. End users download the malicious clone (often searching for a "free" or "mod" version)
6. The app silently sends the victim's credentials to the malicious developer
```

Because the app *looks and functions* identically to the original (same UI, same core gameplay
or features), users have little reason to suspect anything is wrong.

## 5.3 Fake Security Applications

A layered attack that starts on desktop and pivots to mobile:

```
1. Attacker infects the victim's PC with malware
2. Malware waits until the victim logs into their bank account
3. A pop-up appears: "For your security, please install this app on your phone"
4. Victim downloads the fake "security app" from the attacker's app store/link
5. App harvests the victim's banking credentials
6. When the bank sends a legitimate 2FA/SMS code, the fake app intercepts and
   forwards it to the attacker
7. Attacker now has both the password AND the second factor → full account takeover
```

This is precisely why SMS-based 2FA is considered weaker than app-based TOTP or hardware
security keys (FIDO2/WebAuthn) — a compromised device can leak the "second factor" too.

## 5.4 SMiShing (SMS Phishing)

**SMiShing** uses the SMS text-messaging system to lure users into instant action: downloading
malware, visiting a malicious webpage, or calling a fraudulent phone number. The urgency of a
text message (typically read within minutes of arrival) makes it an effective channel.

**Classic pattern:**
> An SMS claiming to be from "XIM Bank Security" tells the recipient there's been suspicious
> activity and to call a provided number immediately. The worried recipient calls; an automated
> recording asks them to key in or speak their card number and PIN "to verify their identity" —
> which the attacker now has.

Other common SMiShing hooks: "you've won a prize, pay a small fee to claim it," fake delivery
notifications ("your package couldn't be delivered, click to reschedule"), and fake
subscription/renewal charges asking the victim to "cancel" via a malicious link.

## 5.5 QRLJacking (QR Code Login Hijacking)

**QRLJacking** exploits the "**Login with QR Code**" pattern used by many modern web apps
(WhatsApp Web being the textbook example) to hijack the login session itself.

```
 1. Attacker initiates a real QR login session with the target web service
 2. Web service returns a legitimate, session-bound QR code to the attacker
 3. Attacker clones that QR code
 4. Attacker builds a phishing webpage embedding the cloned QR code
 5. Attacker sends the phishing page's URL to the victim
 6. Victim scans the QR code with their mobile app, believing it's a normal login
 7. Victim's device ID + login credentials/session token are sent to the attacker
 8. Attacker uses that session to log in to the victim's account
```

Because the victim scans a **real, live** QR code (just relayed by the attacker rather than
generated by them), the login flow looks and feels completely legitimate on the victim's end —
they never see a fake password field to be suspicious of. Once hijacked, the attacker can gain
the victim's GPS location, device ID/IMEI, and SIM details during the login exchange, then use
the compromised session for impersonation, spam, or illegal transactions.

### 🛡️ QRLJacking Defense
- Never scan a QR code received via an unsolicited link, email, or message.
- Prefer login flows that show a **device name/location confirmation** step before finalizing
  the session, and always check that confirmation matches your own device.
- Enable session-activity notifications so a hijacked login triggers an immediate alert.
- Where possible, prefer app-native login (username/password + hardware key or authenticator
  app) over QR-based "convenience" logins for sensitive accounts.
