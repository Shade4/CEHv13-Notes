Because session hijacking is a category of attack rather than a single exploit, defending against it requires layering controls across the network, the application, and the end user. This file organizes the full official countermeasure list — over 45 distinct items — into digestible categories, with practical detail added where useful.

## Top 10 Highest-Impact Controls (Quick Reference)

If you can only implement a handful of controls, these give the most protection per unit of effort:

1. Regenerate the session ID immediately after successful login (kills fixation attacks outright).
2. Set `HttpOnly`, `Secure`, and `SameSite=Strict` (or `Lax`) on every session cookie.
3. Enforce HTTPS on **every** page, not just the login page, and enable HSTS.
4. Use long, cryptographically random session keys — never sequential or timestamp-derived IDs.
5. Implement both an idle timeout and an absolute session timeout.
6. Bind sessions to a consistent IP address and/or User-Agent, and flag mismatches.
7. Destroy sessions server-side on logout — don't just let them expire client-side.
8. Require re-authentication before sensitive actions (transfers, password/email changes).
9. Use multi-factor authentication so a stolen token alone isn't enough.
10. Switch from hub-based to switched networking and monitor for ARP cache poisoning.

## Transport & Cryptography

- Use **Secure Shell (SSH)** or **OpenSSH** to create a secure communication channel.
- Pass authentication cookies **only** over HTTPS connections.
- Ensure data in transit is encrypted, and implement a **defense-in-depth** mechanism (don't rely on a single control).
- Protect authentication cookies with **SSL/TLS**.
- Use **IPsec** to encrypt session information and secure IP communications (see [`07-ipsec-and-advanced-protections.md`](07-ipsec-and-advanced-protections.md) for full detail).
- Use encrypted **VPNs**, such as PPTP and L2TP, for remote connections.
- Use **SFTP**, **AS2**-managed file transfer, or **FTPS** to send data with encryption and digital certificates.
- Employ the Microsoft-based **SMB signing** solution to enable traffic signing.
- Use the encrypted protocols available in the **OpenSSH** suite generally.
- Regularly update platform patches to fix known TCP/IP vulnerabilities (e.g., predictable packet sequences).

## Session & Token Management

- Generate a session ID **after** a successful login, and accept only session IDs generated by the server itself (never accept a client-supplied ID at login time — this is the direct fix for session fixation).
- Use long, random strings/numbers as session keys — never sequential counters or timestamps.
- Implement a `timeout()` mechanism to destroy sessions once they expire.
- Implement an **absolute timeout** regardless of activity-based session timeout, for when a user is inactive.
- Avoid including the session ID in the URL or query string (it ends up in browser history, server logs, and the `Referer` header).
- Reduce the lifespan of a session or cookie as much as usability allows.
- Make the session expire as soon as the user logs out.
- Do not create sessions for unauthenticated users unless strictly necessary.
- **Bind the session to the user's IP address**, and/or check that all requests for a given session originate from the same IP and User-Agent.
- Destroy the associated session **server-side** when a user is deauthenticated — don't simply rely on client-side expiry.
- Monitor session activity for unusual patterns, such as multiple simultaneous logins from different geographic locations.

## Network-Level Protections

- Switch from a hub network to a **switched network** to reduce the risk of ARP spoofing and other session-hijacking attacks that depend on broadcast visibility.
- Configure appropriate internal and external **spoof rules** on gateways.
- Use **IDS products or ARPwatch** for monitoring ARP cache poisoning.

## Application & Browser Controls

- Enable the **`HTTPOnly`** cookie attribute to prevent client-side scripts from accessing session cookies (directly mitigates cookie theft via XSS).
- Use the **`Secure`** flag to ensure cookies are only ever sent over HTTPS, and encrypt them before sending across the network.
- Use the **`SameSite`** cookie attribute to prevent the browser from sending cookies along with cross-site requests (directly mitigates CSRF).
- Restrict cross-site scripts to prevent CSRF from the client side.
- Disable HTTP/TLS **compression mechanisms** (directly mitigates CRIME — see [`02-application-level-session-hijacking.md`](02-application-level-session-hijacking.md#crime-attack)).
- Use restrictive cache directives for all web traffic, especially on sensitive pages: the `Cache-Control: no-cache, no-store` and `Pragma: no-cache` HTTP headers, and/or equivalent `<meta>` tags.
- Enable browsers to verify website authenticity using **network notary servers**.
- Implement **DNS-based authentication of named entities (DANE)**.
- Use **vulnerability scanners** to detect insecure HTTPS session configuration on your sites.
- Upgrade web browsers to the latest versions.
- Ensure client-side and server-side protection software are active and kept up to date.

## Authentication & Authorization

- Use strong authentication mechanisms, such as **Kerberos**, or peer-to-peer VPNs.
- Use **multi-factor authentication (MFA)** to reduce the chances of unauthorized access even if a session token is compromised.
- Use different usernames and passwords for different accounts, to limit blast radius.
- Implement **risk-based authentication** at different levels before granting access to sensitive information.
- Incorporate **re-authentication** and generation of a brand-new session before allowing any sensitive functions (transfers, changing account details, etc.).
- Implement **continuous device verification** to confirm the user who established the session is still the one in control of it.
- Leverage **behavioral biometrics** — typing rhythm, mouse movement, navigation patterns — for continuous authentication throughout a session.
- Implement a **challenge-response mechanism** (e.g., CAPTCHA) when suspicious activity is detected mid-session.
- Perform authentication and integrity verification **between VPN endpoints**, not just at the perimeter.

## Secure Cookie Example

Putting several of the above controls together, a properly hardened session cookie header looks like this:

```http
Set-Cookie: sessionid=8f3e9a1c4b2d7f60; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=1800
```

| Attribute | What It Does |
|---|---|
| `HttpOnly` | Blocks any client-side JavaScript (including injected XSS payloads) from reading this cookie |
| `Secure` | Cookie is only ever transmitted over HTTPS, never plaintext HTTP |
| `SameSite=Strict` | Cookie is never sent on cross-site requests at all, directly neutralizing CSRF (`Lax` is a common, slightly less strict alternative for cookies that need to survive top-level navigation from external links) |
| `Path=/` | Scopes the cookie appropriately — narrow this further if the app supports it |
| `Max-Age=1800` | Hard 30-minute lifespan, limiting the value of a stolen token even if one leaks |

## Web Development Guidelines to Prevent Session Hijacking

Guidance specifically for developers building session-management logic:

- Create session keys with lengthy strings or random numbers, so it's computationally infeasible for an attacker to guess a valid key.
- Regenerate the session ID after a successful login, specifically to prevent session fixation attacks.
- Encrypt the data and session key transferred between user and web servers.
- Implement SSL/TLS to encrypt all information in transit across the network.
- Make sessions expire as soon as the user logs out.
- Prevent eavesdropping within the network generally.
- Reduce the life span of a session or cookie.
- Use restrictive cache directives for all web traffic over HTTP and HTTPS — `Cache-Control: no-cache, no-store` and `Pragma: no-cache` headers/meta tags — on all, or at least all sensitive, pages.
- Do not create sessions for unauthenticated users unless necessary.
- Ensure `HTTPOnly` is set while using cookies for session IDs.
- Use a `Secure` flag to send cookies only in HTTPS requests, and encrypt them before sending across the network.
- Check whether all requests received for the current session originate from the same IP address and user agent.
- Implement continuous device verification to identify whether the user who established the session is still the one in control.
- Implement risk-based authentication at different levels before granting access to sensitive information.
- Perform authentication and integrity verification between VPN endpoints.
- Destroy the associated sessions server-side itself, instead of simply depending on session expiration when a user is deauthenticated.
- Ensure the web application redirects HTTP requests to HTTPS, using either server settings or redirection techniques.
- Incorporate user re-authentication and generation of new sessions before allowing any sensitive functions.
- Rely on web frameworks that provide highly secure session-ID generation, rather than rolling your own session management.
- **Enforce HTTPS on all pages of the web application, not just the login page.**

## Web User Guidelines to Prevent Session Hijacking

Guidance for end users defending their own sessions:

- Do not click on links received through emails or instant messages (IMs).
- Use firewalls to prevent malicious content from entering the network, and to restrict cookies.
- Ensure the website is certified by an appropriate certifying authority before entering credentials.
- Clear browser history, offline content, and cookies after every confidential or sensitive transaction.
- Prefer HTTPS over HTTP whenever transmitting sensitive or confidential data.
- Log out of applications by clicking the actual logout button, rather than just closing the browser tab/window.
- Verify and disable browser add-ons from untrusted sites; enable add-ons only when necessary.
- Use a one-time password for critical data transactions (e.g., credit-card payments).
- Frequently update anti-virus signatures, to prevent automatic installation of malware that attempts to steal cookies.
- Avoid accessing sensitive accounts or conducting financial transactions over **public Wi-Fi**.
- Disable auto-connect to open Wi-Fi networks.
- Keep your operating system, web browsers, and installed plugins updated.
- Use encrypted messaging and email services for sensitive communication.
- Avoid saving passwords in the browser.
- Use **incognito/private mode** on shared computers.
- Be cautious about granting apps access to sensitive information or device features.
- Use custom session handlers for storing and handling session tokens where the application supports it.
